# 项目代码审查与整理

请对整个项目进行一次全面的代码审查、整理与必要的重构，遵循以下要求：

1. **架构设计**：检查模块划分、职责分配及函数设计是否合理，确保模块内部高内聚、模块之间低耦合，避免职责混乱和不必要的依赖。
2. **MVVM 与职责边界（适用于 WPF 等具有视图层的项目）**：结合项目现有结构，检查 View、ViewModel 与业务及数据层的职责是否清晰。
   - **View** 负责界面展示和视图交互。焦点、滚动、动画及控件特有行为可以保留在 code-behind；可独立于界面运行的业务规则、数据访问和持久化逻辑应放在相应业务或数据层。
   - **ViewModel** 负责界面状态、命令和用例协调，通过属性通知、数据绑定与命令连接 View。避免直接依赖具体 Window、控件或通过查找控件读取业务状态，也避免集中承担文件解析、存储和播放引擎等底层实现。
   - **Model 与业务、数据层** 负责领域数据、业务规则及相关操作，不依赖具体视图或 ViewModel；按现有项目规模合理划分，不机械增加层次。
   - **状态与生命周期**：检查状态来源是否明确，属性及集合通知、命令可执行状态是否正确更新；检查异步结果更新、UI 线程访问、事件订阅与释放，避免界面和实际状态不一致。
   - **整改尺度**：以职责清晰、降低耦合和便于验证为目标，不以 code-behind 为空、类名或目录形式作为合格标准。不强制引入 MVVM 框架、依赖注入容器、消息总线或通用仓储；保留合理实现，仅对确有问题的部分做最小必要调整。重大架构迁移先提出方案。
   - **验证**：对调整涉及的状态变化、命令和业务规则进行适用验证；绑定、焦点、滚动等视图行为通过对应 UI 检查确认，不能仅凭 ViewModel 测试通过判定界面正确。
3. **代码质量**：检查程序逻辑、命名、异常处理及可读性，消除不必要的复杂性、冗余与重复。优先采用简单、直接、清晰的实现方式，避免过度设计、过度抽象和不必要的高级语法。允许少量简单重复，但应合理复用复杂的重复逻辑。仅在能够降低整体复杂度、提高可维护性时引入抽象。不以减少代码行数、函数或模块数量为目标。
4. **问题整改**：修复发现的设计缺陷、潜在错误及其他必要问题。坚持最小必要修改原则，保持现有功能、外部接口及预期行为不变。对于已经合理的实现，不做无意义的重构；对于可能改变功能或涉及重大架构调整的问题，先提出方案，不擅自实施。
5. **项目清理**：清理确认无用的文件、临时文件及构建垃圾，必要时完善 .gitignore。不得误删项目资源、配置及用户数据。同步更新相关文档，确保文档与实际代码一致。
6. **验证与提交**：完成修改后，运行适用的构建、测试及静态检查，确认没有引入新的问题。检查 Git 状态，保留原有未提交改动，不擅自切换或合并分支，仅提交本次任务涉及的修改。验证通过后提交代码并推送至当前分支对应的 GitHub 远程分支，不进行强制推送。若验证失败或提交条件不满足，说明原因，不强行提交或推送。

最后，简要报告发现的主要问题、整改内容、删除的文件、验证结果、Git 提交记录及尚未解决的问题。审查发现应区分“正确性必需修复”“维护性建议”和“可选风格调整”，不将 MVVM 风格偏好作为功能缺陷。
